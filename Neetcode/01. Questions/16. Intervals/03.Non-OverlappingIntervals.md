# [435. Non-overlapping Intervals](https://leetcode.com/problems/non-overlapping-intervals/)


Given an array of intervals intervals where intervals[i] = [starti, endi], return the minimum number of intervals you need to remove to make the rest of the intervals non-overlapping.
**Example 1:**

![[non-overlapping-intervals-example.svg]]

```text
Input: intervals = [[1,2],[2,3],[3,4],[1,3]]
Output: 1
Explanation: [1,3] can be removed and the rest of the intervals are non-overlapping.
```

**Example 2:**

```text
Input: intervals = [[1,2],[1,2],[1,2]]
Output: 2
Explanation: You need to remove two [1,2] to make the rest of the intervals non-overlapping.
```

**Example 3:**

```text
Input: intervals = [[1,2],[2,3]]
Output: 0
Explanation: You don't need to remove any of the intervals since they're already non-overlapping.
```

Constraints:

- 1 <= intervals.length <= 10<sup>5</sup>
- intervals[i].length == 2
- -5 * 10<sup>4</sup> <= starti < endi <= 5 * 10<sup>4</sup>

---

## Solution

### Intuition
This is the classic [[0.GreedyGuide|Greedy]] [[Interval Scheduling]] problem. Sorting by end time lets us always keep the interval that finishes earliest, leaving the most room for future intervals. Every time a new interval overlaps the current boundary, we count it as removed and keep the one with the smaller end time.

### Approach: Sort by end time + greedy sweep

Sort by end time. Track the end of the last kept interval. For each new interval, if it overlaps (starts before the last end), increment the removal count; otherwise advance the boundary.

```python
class Solution:
    def eraseOverlapIntervals(self, intervals: list[list[int]]) -> int:
        intervals.sort(key=lambda x: x[1])  # sort by end time (greedy key)
        removed = 0
        prev_end = intervals[0][1]

        for start, end in intervals[1:]:
            if start < prev_end:        # overlap: remove the one with larger end
                removed += 1
                # prev_end stays the same (we implicitly keep the earlier-ending interval)
            else:                       # no overlap: advance boundary
                prev_end = end

        return removed
```

> We keep `prev_end` unchanged when removing, because we are removing the current (later-ending) interval and keeping the previous one. The boundary does not advance.

### Walkthrough
Input: `[[1,2],[2,3],[3,4],[1,3]]` sorted by end: `[[1,2],[2,3],[1,3],[3,4]]`

| Current | prev_end | Overlap (start < prev_end)? | removed | prev_end after |
|---------|----------|-----------------------------|---------|----------------|
| [2,3] | 2 | 2 < 2? No | 0 | 3 |
| [1,3] | 3 | 1 < 3? Yes | 1 | 3 (unchanged) |
| [3,4] | 3 | 3 < 3? No | 1 | 4 |

Output: `1`

### Complexity
- **Time:** O(n log n). Sorting dominates; sweep is O(n).
- **Space:** O(1). Only a counter and a boundary variable are maintained.

### Key concepts to review
- [[0.GreedyGuide|Greedy]] - sort-by-end is the canonical greedy choice for interval scheduling
- [[Interval Scheduling]] - directly applies the "earliest deadline first" rule
- [[Sorting]] - the algorithm only works correctly when sorted by end time
- [[02.MergeInterval]] - related: that problem merges overlaps; this counts removals

### Common pitfalls
- Sorting by start time instead of end time, which gives wrong greedy choices.
- Using `<=` in the overlap check: touching boundaries like [1,2] and [2,3] are NOT overlapping and should not be counted.
- Advancing `prev_end` on removal, which incorrectly expands the taken boundary.
- Off-by-one on seeding: seed `prev_end` from the first interval's end, not start.
