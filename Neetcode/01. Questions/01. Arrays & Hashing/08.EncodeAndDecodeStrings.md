# [271. Encode and Decode Strings](https://leetcode.com/problems/encode-and-decode-strings/)

Design an algorithm to encode a list of strings to a string. The encoded string is then sent over the network and is decoded back to the original list of strings.

Please implement encode and decode


**Example 1:**

```text
Input: ["lint","code","love","you"]
Output: ["lint","code","love","you"]
Explanation:
One possible encode method is: "lint:;code:;love:;you"
```

**Example 2:**

```text
Input: ["we", "say", ":", "yes"]
Output: ["we", "say", ":", "yes"]
Explanation:
One possible encode method is: "we:;say:;:::;yes"
```

---

## Solution

### Intuition

The whole challenge is that any delimiter you pick could appear inside a string, so a plain separator like `,` is ambiguous. The robust fix is length prefixing: write each string as `<length>#<string>`. The decoder reads the number up to the `#`, then knows exactly how many characters to consume next, regardless of what those characters are. This is the standard length-prefixed framing used in real network protocols.

### Approach

Encode by prefixing each string with its length and a `#` marker. Decode by reading digits until a `#`, parsing the count, then slicing exactly that many characters.

```python
class Solution:
    def encode(self, strs: list[str]) -> str:
        # each chunk is "<len>#<string>"; length tells the decoder how much to read
        return "".join(f"{len(s)}#{s}" for s in strs)

    def decode(self, s: str) -> list[str]:
        res: list[str] = []
        i = 0
        while i < len(s):
            j = i
            while s[j] != "#":      # advance to the delimiter to read the length digits
                j += 1
            length = int(s[i:j])    # number of chars in the next string
            start = j + 1
            res.append(s[start:start + length])   # slice exactly that many chars
            i = start + length      # jump past this chunk to the next length prefix
        return res
```

> Why length prefixing instead of a separator character? Because the strings may contain any character, including `#` or `:`. The count tells the decoder precisely where each string ends, so the content is never misread as a delimiter.

**Encoded layout for `["lint", "code"]`:**

| Chunk | Length | Marker | Payload |
|---|---:|:---:|---|
| 1 | 4 | `#` | `lint` |
| 2 | 4 | `#` | `code` |

### Walkthrough

`strs = ["lint", "code"]`

Encode -> `"4#lint4#code"`

| i | read length up to # | length | slice | res | next i |
|---|---------------------|--------|-------|-----|--------|
| 0 | "4"                 | 4      | s[2:6] = "lint" | ["lint"] | 6 |
| 6 | "4"                 | 4      | s[8:12] = "code" | ["lint","code"] | 12 |

Output: `["lint", "code"]`.

### Complexity

- **Time:** O(n) for both encode and decode, where n is the total number of characters across all strings; each character is processed a constant number of times.
- **Space:** O(n) for the encoded string and the decoded list.

### Key concepts to review

- [[String Encoding]] - length-prefixed framing is the canonical way to serialize variable-length data unambiguously.

### Common pitfalls

- Picking a single delimiter character and assuming it never appears in the data; it can, which corrupts decoding.
- Off-by-one when slicing: the string starts at `j + 1` (just past `#`) and runs for `length` characters.
- Forgetting that an empty string encodes as `0#`, which the length-prefix scheme handles correctly.
