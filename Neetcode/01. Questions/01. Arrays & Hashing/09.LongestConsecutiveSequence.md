# 128. Longest Consecutive Sequence

Given an unsorted array of integers nums, return the length of the longest consecutive elements sequence.

You must write an algorithm that runs in O(n) time.

 

**Example 1:**

![[longest-consecutive-sequence-example-1.svg]]

```text
Input: nums = [100,4,200,1,3,2]
Output: 4
Explanation: The longest consecutive elements sequence is [1, 2, 3, 4]. Therefore its length is 4.
```

**Example 2:**

```text
Input: nums = [0,3,7,2,5,8,4,6,0,1]
Output: 9
```

Constraints:

- 0 <= nums.length <= 10<sup>5</sup>
- -10<sup>9</sup> <= nums[i] <= 10<sup>9</sup>

---

## Solution

### Intuition

Sorting would find consecutive runs easily but costs O(n log n), and the problem demands O(n). The key insight: put everything in a [[Set]] for O(1) lookups, then only start counting a run from its true beginning - a number `x` is a sequence start exactly when `x - 1` is absent. From a start we walk upward, `x+1`, `x+2`, ..., counting the run. Because each number is only ever extended from its unique start, the total work stays linear.

### Approach 1: Sorting (for contrast)

Sort, then scan for the longest run of consecutive values (skipping duplicates).

```python
class Solution:
    def longestConsecutive(self, nums: list[int]) -> int:
        if not nums:
            return 0
        nums = sorted(set(nums))
        longest = streak = 1
        for i in range(1, len(nums)):
            if nums[i] == nums[i - 1] + 1:
                streak += 1
                longest = max(longest, streak)
            else:
                streak = 1
        return longest
```

Correct, but O(n log n) from the sort, which fails the time requirement.

### Approach 2: Hash set, count only from starts (optimal)

Build a set. For each value that has no left neighbor (a sequence start), walk right counting the run length and track the max.

```python
class Solution:
    def longestConsecutive(self, nums: list[int]) -> int:
        num_set = set(nums)          # O(1) membership tests
        longest = 0

        for num in num_set:
            if num - 1 not in num_set:    # only start at the beginning of a run
                length = 1
                while num + length in num_set:
                    length += 1
                longest = max(longest, length)

        return longest
```

> The `num - 1 not in num_set` guard is what keeps this O(n). Without it, every element could trigger a full upward walk, degrading to O(n^2). With it, each run is traversed exactly once, from its start.

### Walkthrough

`nums = [100, 4, 200, 1, 3, 2]`, set = `{100, 4, 200, 1, 3, 2}`

| num | is start? (num-1 absent) | walk | run length | longest |
|-----|--------------------------|------|------------|---------|
| 100 | yes (99 absent)          | 101 absent | 1 | 1 |
| 4   | no (3 present)           | skip | -          | 1 |
| 200 | yes (199 absent)         | 201 absent | 1 | 1 |
| 1   | yes (0 absent)           | 2,3,4 present | 4 | 4 |
| 3   | no (2 present)           | skip | -          | 4 |
| 2   | no (1 present)           | skip | -          | 4 |

Output: `4`.

### Complexity

- **Time:** O(n). Each number is visited once when iterating the set, and each is part of exactly one upward walk.
- **Space:** O(n). The set stores all unique values.

### Key concepts to review

- [[Set]] - O(1) membership is what enables both the start-check and the upward walk.
- [[Hash Map]] - a set is a hash map without values; same O(1) lookup engine.
- [[Sorting]] - the intuitive but too-slow alternative at O(n log n).

### Common pitfalls

- Walking upward from every element instead of only from run starts, which makes it O(n^2).
- Forgetting to handle the empty input, which should return 0.
- Not deduplicating; a set handles this for free, but a list-based approach would double-count.
