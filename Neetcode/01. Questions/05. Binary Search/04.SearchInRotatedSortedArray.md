# 33. Search in Rotated Sorted Array


There is an integer array nums sorted in ascending order (with distinct values).

Prior to being passed to your function, nums is possibly rotated at an unknown pivot index k (1 <= k < nums.length) such that the resulting array is [nums[k], nums[k+1], ..., nums[n-1], nums[0], nums[1], ..., nums[k-1]] (0-indexed). For example, [0,1,2,4,5,6,7] might be rotated at pivot index 3 and become [4,5,6,7,0,1,2].

Given the array nums after the possible rotation and an integer target, return the index of target if it is in nums, or -1 if it is not in nums.

You must write an algorithm with O(log n) runtime complexity.

 

**Example 1:**

![[search-in-rotated-sorted-array-example-1.svg]]

```
Input: nums = [4,5,6,7,0,1,2], target = 0
Output: 4
```
**Example 2:**
```
Input: nums = [4,5,6,7,0,1,2], target = 3
Output: -1
```
**Example 3:**
```
Input: nums = [1], target = 0
Output: -1
```

Constraints:

- 1 <= nums.length <= 5000
- -10<sup>4</sup> <= nums[i] <= 10<sup>4</sup>
- All values of nums are unique.
- nums is an ascending array that is possibly rotated.
- -10<sup>4</sup> <= target <= 10<sup>4</sup>

## Solution

### Intuition
A rotated sorted array always has at least one fully sorted half on either side of `mid`. The key insight: by comparing `nums[mid]` to `nums[lo]` we can tell which half is sorted, and within a sorted half we can decide in O(1) whether the target lies inside it. That lets us discard half each step, preserving the O(log n) guarantee of [[0.BinarySearchGuide|Binary Search]].

### Approach
At each step, find `mid`. If `nums[lo] <= nums[mid]`, the left half is sorted; check whether `target` falls in `[nums[lo], nums[mid])` and move accordingly. Otherwise the right half is sorted; check `(nums[mid], nums[right]]`.

```python
class Solution:
    def search(self, nums: list[int], target: int) -> int:
        lo, hi = 0, len(nums) - 1  # inclusive bounds

        while lo <= hi:
            mid = lo + (hi - lo) // 2
            if nums[mid] == target:
                return mid

            if nums[lo] <= nums[mid]:          # left half [lo..mid] is sorted
                if nums[lo] <= target < nums[mid]:
                    hi = mid - 1               # target in sorted left half
                else:
                    lo = mid + 1
            else:                              # right half [mid..hi] is sorted
                if nums[mid] < target <= nums[hi]:
                    lo = mid + 1               # target in sorted right half
                else:
                    hi = mid - 1

        return -1
```

> The comparison `nums[lo] <= nums[mid]` must use `<=`, not `<`. When the window narrows to a single element `lo == mid`, the left half is trivially "sorted", and `<=` keeps that branch correct.

### Walkthrough
`nums = [4,5,6,7,0,1,2]`, `target = 0`.

| lo | hi | mid | nums[mid] | sorted half | target there? | action |
|----|----|-----|-----------|-------------|---------------|--------|
| 0 | 6 | 3 | 7 | left [4..7] | 0 not in [4,7) | lo = 4 |
| 4 | 6 | 5 | 1 | left [0..1] | 0 in [0,1) | hi = 4 |
| 4 | 4 | 4 | 0 | - | nums[mid]==target | return 4 |

Output: `4`.

### Complexity
- **Time:** O(log n). One half of the window is discarded each iteration.
- **Space:** O(1). Only index variables.

### Key concepts to review
- [[0.BinarySearchGuide|Binary Search]] - adapt the template by first detecting which half is sorted, then testing range membership; builds on [[01.BinarySearch]].

### Common pitfalls
- Using `<` instead of `<=` in `nums[lo] <= nums[mid]` breaks single-element and two-element windows.
- Getting the range bounds inclusive/exclusive wrong (left half is `[nums[lo], nums[mid])`, right half is `(nums[mid], nums[hi]]`).
- Forgetting to check `nums[mid] == target` first, before the half analysis.
